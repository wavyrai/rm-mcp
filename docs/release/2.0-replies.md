## Issue #1: usertoken always empty after registration on Windows (+ HTTP/SSE request)

> Suggested action: close after posting, and open a separate issue for HTTP transport if the owner wants to track it.

Thanks for the detailed report, and sorry it took this long.

The empty `usertoken` is expected: registration only returns the long-lived device token, and the server exchanges it for a short-lived user token when it starts. That part wasn't the bug. What did break on Windows was everything around it: setup printed a config with POSIX-only quoting, image rendering needed Cairo, and Claude Desktop couldn't find `uvx`.

rm-mcp 2.0 fixes those:

- `uvx rm-mcp@latest setup` saves the token in its own file (`%APPDATA%\rm-mcp\token.json`) and offers to add rm-mcp to Claude Desktop itself, with the full path to `uvx.exe`. No token goes into the config any more, so there is nothing to quote.
- Rendering uses PyMuPDF only; no Cairo or other system libraries.
- There's also a Claude Desktop bundle (`.mcpb`) on the release page: open it, paste a one-time code, done.
- `uvx rm-mcp@latest doctor` checks the token, the connection, `uvx` and the Desktop config, and says what to fix.
- CI now runs the test suite on Windows.

On HTTP/SSE: 2.0 still runs over stdio only. With the bundle, Claude Desktop on Windows starts the server itself, which should remove the need for a URL-based server. If it still doesn't work for you, please tell us what Claude Desktop logs and we'll look at an HTTP mode.

## Issue #6: `--setup` always gives the same token; 400 on the root index

> Suggested action: close after posting; ask the reporter to reopen if 2.0 doesn't fix it.

Thanks for reporting this, and sorry for the long wait. Two separate problems were most likely behind it, and 2.0 fixes both.

1. **The 400 on the root index** came from a server-side change by reMarkable in May 2026: downloads now need an `rm-filename` header. rm-mcp 2.0 sends it on every request (credit to PR #7 for tracking it down), and a daily canary now checks the real API so a change like this gets caught early.
2. **Re-running setup didn't help** because older versions let a `REMARKABLE_TOKEN` in the client config win over a new registration, so the server kept using the old token whatever setup printed. 2.0 keeps its token in its own file (`~/Library/Application Support/rm-mcp/token.json` on macOS) and reads that file first. Running setup again replaces it, and a running server picks the new one up.

To move over:

```bash
uvx rm-mcp@latest setup
uvx rm-mcp@latest doctor
```

Setup offers to rewrite your Claude Desktop and Claude Code entries without the old token. You can remove the stale `REMARKABLE_TOKEN` from any other client config. If you cleaned up devices at my.remarkable.com, the new registration shows up there as "desktop-macos".

## Issue #9: ModuleNotFoundError: No module named 'mcp.server.fastmcp'

> Suggested action: close after posting.

Thanks for the report, and thanks to tuzumkuru for the diagnosis and the workaround. The MCP Python SDK 2.0 renamed `FastMCP`, and rm-mcp 0.7 allowed any `mcp>=1.0`, so fresh installs picked up 2.x and failed on import.

rm-mcp 2.0 is built on the SDK 2.x API and pins `mcp>=2.3,<3`, so this can't recur with a future SDK major. Please remove any `--with "mcp<2"` workaround from your config and run:

```bash
uvx rm-mcp@latest setup
```

It can also rewrite your Claude Desktop entry for you (it keeps a `.bak` of the old file).

## PR #7: Send the rm-filename header on /sync/v3/files downloads

> Suggested action: close as superseded, with thanks.

Thank you for this, and for the clear write-up with links to the rmapi and rmapi-js fixes. It was exactly the right diagnosis. Sorry it sat unmerged while the library was broken for everyone.

The 2.0 rewrite includes the same fix: every blob request sends `rm-filename` (`root.docSchema`, `<uuid>.docSchema`, `<uuid>.metadata` and so on), and uploads send it along with the `x-goog-hash` checksum. The sync client was rebuilt around incremental sync and a hash-verified blob cache, so this branch no longer applies. I'm closing it as superseded, but your PR is what pointed us at the header, and the 2.0 changelog credits the report. A daily canary now probes the real API so we notice this kind of change ourselves.
